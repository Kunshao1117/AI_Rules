# Phase 4B-1 Skill Architecture Disposition Freeze

This owner-linked migration Reference freezes classification under
`Shared/skill-governance.md`. It is not a second runtime registry, Agent roster,
trigger engine, permission source or physical migration instruction to execute now.
The table is the Phase 4B-1 historical classification snapshot. A1 execution is
recorded in `legacy-skill-migration.md` and its exact path/provenance mapping;
other target paths remain concepts until their separately scoped batch exists.
Existing policy/Agent targets mean integrate unique content without duplicating
their contracts; proposed method references carry examples, never new governance.

## Inventory and frozen decisions

The denominator is actual `Shared/skills/*/SKILL.md`, not index numbering.
At the Phase 4B-1 freeze, 64 files existed and the index had 62 Skill rows plus
a policy pointer. Current inventory is measured from source; an A1 migrated row
is resolved through the migration mapping rather than assumed physically active.
The omissions are team-specialist-memory-closure and
team-memory-closure-delivery-artifact. Do not repair either in this migration.
Two empty historical reflection directories are not Skills or cleanup targets.
Current lifecycle below distinguishes retained legacy, mixed methods, frozen
Memory, pending migration and structured-reasoning newly inactive for general use.
RETIRE describes the eventual disposition, not a deletion performed in Phase 4B-1.

Memory is the census spelling of the frozen Memory Subsystem. All six Memory
Skills are deferred intact. High coupling never permits changing or retiring
Memory-required text, paths, anchors, receipt shapes or persistent Context behavior.
project-context-protocol is Policy in concept but defer-sensitive-migration in
execution. No new Agent is created; MOVE_TO_AGENT maps only to Phase 3 roles.
GitNexus CLI remains a method Skill, KEEP_BUT_REWRITE in its Optional Pack.
The other four GitNexus method Skills remain distinct; only the guide is Reference.
Supabase integration, remote operations and Postgres optimization remain distinct.
execute_sql versus apply_migration is an environment/context routing issue to
resolve during the Supabase batch, not authorization to merge or repair them now.
