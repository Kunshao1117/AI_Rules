# M3-to-M4 Frozen Memory Team Compatibility Procedure

This is a temporary, non-invocable compatibility procedure for existing frozen
Memory consumers after the four legacy Team Memory SKILL.md entries leave the
Shared Skill tree. It is not a Skill, formal Agent, ordinary vNext workflow,
authorization owner, or new route into protected mutation. New ordinary work
uses `../memory-governance.md`, `workflow-memory-evidence.md`, and `memory-ops`
for review and method. Keep the existing `memory-docs` and `memory-closure`
IDs only as legacy receipt/packet identities; do not register new Agents.

## Read-only attribution

An existing frozen `memory-docs` consumer may read current source/card evidence
and return `memory-review-evidence.md` with documentation, index, generated-copy
and handoff impact. Before issuing a legacy `memory-docs` receipt, verify its
independent candidate binding is current and eligible after validation and
review acceptance for the current delivery-slice revision. Missing, stale or
ineligible binding leaves that legacy receipt blocked or unverified. This
legacy gate does not apply to an ordinary M1 Memory Impact Review. The frozen
phase is read-only. Its role instance and execution
channel cannot be reused for the protected `memory-closure` consumer. The old
artifact fields remain interpretable through the corresponding legacy aliases.

## Protected continuation

For a legacy frozen consumer that actually needs `.agents/memory/**` mutation,
`memory_commit`, reindex or index sync, classify the physical operation as
`frozen_memory_action` under `../authorization-resolution.md` and the existing
protected-action/phase registries. Resolve the current
`memory-closure-bundle-contract.md` through `completion_bundle_ref`; the bundle
is a dependency index and grants no authority. Never fabricate a bundle or
retroactively attach candidates to an earlier execution spec.

Before any action, require the exact existing owner card and target scope,
current source and `delivery_slice_revision`, accepted non-stale validation and
review artifacts, the independently bound `memory-docs` candidate and receipt,
expiry, station identity, and phase-specific current authorization. The
`memory-closure` role instance/channel must be distinct from `memory-docs`.
Only an eligible `protected-memory-write` binding may permit the minimum
owner-confirmed card write. Only a separately eligible
`protected-memory-commit` binding after that write may permit `memory_commit`.
Record distinct write and commit receipts, partial failure and remaining risk
using `memory-update-sync-evidence.md`. Reindex and index sync remain frozen
physical actions with their own applicable authorization; neither follows
automatically from a write or commit.

An accepted repair that changes the delivery slice increments its revision and
stales all earlier Memory receipts for the current closeout. Missing, expired,
revoked, mismatched or unverified binding, ambiguous owner, changed scope,
stale receipt, missing independent role/channel, or unavailable provider keeps
the affected mutation `blocked` or `unverified`. Do not replace the legacy
protected worker with Main or Conditional Implementer. Do not claim
`process-complete` without the current no-write or committed receipt required
by the frozen completion contract. A `source-level-explicit` exception may
leave protected follow-up pending; it never supplies deferred write authority.

M4 has defined the ordinary target contract, but this procedure remains
`LEGACY_COMPAT_ONLY` for current frozen and unmigrated consumers. It supplies
no activation evidence. Keep its exact role/channel, bundle, phase and receipt
requirements until M5 proves the last applicable project/runtime consumer has
been migrated or safely retained. An unknown or user-modified old runtime Skill
blocks ordinary cutover for that project; preserve it and resolve its loader
status instead of ignoring or deleting it. M3 changed document lookup and
active Shared Skill identity only.
